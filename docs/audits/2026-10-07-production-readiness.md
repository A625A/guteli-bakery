# Güteli production readiness audit

Audit date: 2026-10-07, America/Guatemala. **Decision: not ready to accept real money.** This is an audit and proposed plan, not implementation or launch approval.

The application is substantially beyond a static demo: catalog management, durable order requests, secure administration, image ingestion, and order operations exist. The commercial gaps are verified payments, production capacity, final-price acceptance, payment-aware order rules, complete WhatsApp handoff, and operational release evidence.

## B. Blocking gaps and risk order

1. **P0 — no payment system.** Establish the real provider contract, then collect/verify through server-owned attempts and authenticated webhooks/reconciliation. No screenshot, redirect query or WhatsApp text may change payment status.
2. **P0 — no date capacity and no safe release contract.** A local timer cannot make an external ACH payment impossible. Reserve capacity while payment is pending/unknown; release only after proven non-payability/terminality. If that cannot be proven for a method, do not offer it with automatic short-lived reservations.
3. **P0 — no frozen, customer-approved full payable total.** Delivery must be quoted first. A later quote/product edit cannot silently alter an active payment attempt or amount already collected.
4. **P0 — missing commercial operations evidence.** Production environment, private ingress, HTTPS, backups/restore, owner recovery, provider configuration and DB/browser/security acceptance are gates before money.
5. **P1 — recovery and lifecycle gaps.** Reload idempotency, failed/abandoned/in-flight/refunded payments, cancellation vs refund, late success, duplicate events and separate production status all need explicit handling.
6. **P1 — incomplete owner/customer handoff.** Add a paid-work queue, acknowledgement, clear pending/confirmed receipt and optional Click-to-Chat; the admin DB is the reliable record even when WhatsApp never opens.
7. **P1 — operational content/privacy.** Actual prices/sale units/photos, pickup address, hours, order cutoff, capacity, refund terms and retention require owner decisions. Do not inherit old retention numbers as approval.

## F. Launch checklist

All items below are requirements, **not completed checks**. Link evidence and approving owner to the eventual release record.

### Must have before accepting real money

- [ ] Approve provider/methods, merchant eligibility, fees/taxes/settlement terms, actual signed payload contract and safe capacity-release policy (ticket 01).
- [ ] Approve production-day accounting, limits/weights, unavailable dates, advance cutoff, fulfillment pricing, cancellation/refund policy and contact details.
- [ ] Final customer-approved GTQ total matches immutable order and provider amount; no active checkout exists for unquoted delivery.
- [ ] Last-slot race, retry/reload, duplicate/out-of-order webhook, unknown provider result, expiry/payment race, partial/full refund and downtime recovery tests pass.
- [ ] Verified payment is the only normal prepaid path to confirmation; no admin/client bypass; late mismatched funds enter a visible resolution queue.
- [ ] Pending/unknown payment keeps its allocation until safely resolved. Worker downtime never silently releases a payable reservation.
- [ ] Owner can find/acknowledge paid orders without WhatsApp; agree a staffed dashboard-check schedule and response expectation. If this is not acceptable, select an additional reliable alert channel before launch.
- [ ] Complete encoded WhatsApp message and copy fallback work on mobile/desktop; customer must press Send; message never grants payment authority.
- [ ] Existing product CRUD, auth/MFA, order handling and image operations pass isolated integration and E2E regression. Owner completes a plain-Spanish acceptance walkthrough and recovery drill.
- [ ] Hardened runtime injects independent server secrets; live public configuration is built deliberately; demo state is explicit; production refuses unsafe/missing config.
- [ ] HTTPS/DNS/certificate renewal and HTTP redirect tested; DB remains private; app bypass blocked; proxy strips spoofed client headers; secrets/PII absent from logs and bundles.
- [ ] Durable database/images with encrypted off-host backups, restore to an isolated target, approved RPO/RTO and retention. No production migration/seed on app boot.
- [ ] Readiness includes required schema/config/storage; monitor DB, webhook failures, pending-payment age, reconciliation heartbeat, backup freshness and disk.
- [ ] Complete privacy/retention/access logging and receipt-token policy; merchant issues required receipts/invoices according to owner/accountant-confirmed obligations.
- [ ] Fresh dependency/advisory review and documented release rollback; compiled candidate is tested under HTTPS with an isolated DB.
- [ ] Separate explicit approval for public deployment and any capped live-payment/refund acceptance test; do not infer it from implementation approval.

### Optional after a reliable launch

- Automated polygon-based Q10/Q35 delivery quoting using the existing design and owner-approved real coverage.
- Paid WhatsApp Business messaging, email/push alerts, WebSockets, advanced analytics or customer accounts.
- S3 adapter when the chosen hosting lifecycle requires it; multi-instance hosting only when demonstrated demand warrants it.
- Per-product/date overrides if a simple approved weighted daily budget suffices initially; partial fulfillment and warehouse forecasting remain out of scope.
- Broad visual redesign or specialist design-plugin installation. Fix evidenced accessibility/usability defects first.

## Recommended order and first ticket

Resolve the provider contract first; then final-total approval and resumable checkout, date capacity, actual payment attempts, verified collection, safe release/refunds, and owner/customer operational flows. Runtime, backup and privacy preparation can progress independently once approved. Finish with isolated integration/browser/HTTPS/restore evidence and a separate launch decision.

**Start with ticket 01: prove the Recurrente checkout and bank-transfer contract in Sandbox.** Its deliverable is concrete provider evidence, especially payable-session expiration/in-flight ACH behavior and ambiguous creation recovery. Building short-lived production reservations before resolving this risks either overselling or retaining capacity indefinitely. If merchant/Sandbox access is unavailable, the ticket remains blocked on that external prerequisite; no fake integration substitutes for it.
