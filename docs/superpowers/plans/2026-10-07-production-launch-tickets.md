## Execution order

Start with **01**, because the provider's terminal-payment and creation-recovery contracts determine whether automatic reservation expiry can safely exist. If Sandbox access or provider answers are unavailable, record that external blocker; do not substitute a fake payment integration.

After approval, 02 and 10 can proceed independently while provider prerequisites resolve. The principal customer path is 02 → 03 → 04 → 05 → 06 → 07, with 04 also requiring 01. Then complete 08 and 09 using verified payment state. Storage/recovery (11) follows the runtime choice; privacy (12) follows recovery credentials in 02. Owner/mobile acceptance (13) follows the customer and admin slices. 14 depends on all required evidence. This is a dependency map, not an instruction to spawn implementation agents.

Each ticket is a narrow behavior slice, not separate database/API/UI jobs. Ticket 01 is an evidence spike; 10–12 are operational/vertical recovery controls. If a future implementation exceeds a fresh context window, split a behavior scenario before coding rather than landing half an unsafe payment flow.
