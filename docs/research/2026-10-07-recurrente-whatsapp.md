# Recurrente and WhatsApp: production integration research

Research date: **2026-10-07, America/Guatemala**. Scope: public, first-party documentation only; no account inspection, credentials, sandbox transactions, real payments, external messages, or production changes. “Documented” below means verified against public documentation, not exercised against Güteli's account. Recommendations are proposed application design, not existing functionality.

## Decision

Recurrente is a plausible hosted-payment provider for Güteli, including Guatemalan ACH transfers. **It is not yet proven to satisfy the strict requirement that nobody can pay after their production capacity becomes unavailable.** A provider checkout expiry and a local reservation timeout do not establish cancellation of an in-flight bank transfer. Resolve that contract before enabling automated capacity release or accepting real money.

Use hosted checkout, server-owned order totals, PostgreSQL reservations and payment reconciliation, an authenticated admin paid-order queue, and optional WhatsApp Click-to-Chat. Keep GTQ and one-time payments for the initial scope. Do not add wallets, subscriptions, installments, connected accounts, or a second database.

## Webhooks, replay protection and reconciliation

The current recommendation is unified `intent.*` events. Legacy and unified formats can both be delivered for one payment. Subscribe/process only the selected payment contract; `refund.*` and `dispute.*` remain separate. Intermediate card states can normalize to pending. [Migration guide](https://docs.recurrente.com/guias-espanol/guias/migrar-a-webhooks-unificados)

Recurrente signs raw request bytes using `svix-id`, `svix-timestamp` and `svix-signature`; the message ID stays stable on retries. Its guide recommends the Svix verifier, describes HMAC-SHA256 and timestamp checking, and documents retries after non-2xx responses: immediate, one minute, five minutes, thirty minutes, two hours and six hours. The endpoint has its own `whsec_*` signing secret. [Webhook guide](https://docs.recurrente.com/guias-espanol/comenzar/webhooks)

Proposed security and processing contract:

1. Require configured secret; reject oversized bodies, missing/invalid signatures and unacceptable timestamp skew. Verify raw bytes before JSON parsing. Use the maintained official verifier and test stale/future timestamps rather than copying handwritten HMAC code. [Svix verification](https://docs.svix.com/receiving/verifying-payloads/how)
2. Persist a bounded, protected event inbox before acknowledging. Unique key includes provider environment/account/endpoint identity and authenticated `svix-id`. Return non-2xx on failed durable receipt so retries remain useful. Redact customer data from operational logs.
3. Store canonical provider intent/payment identity separately from message identity. A later success must not be discarded because an earlier pending event had the same intent ID. An alternate-format duplicate must not confirm the order twice.
4. Retrieve checkout and intent server-side. Match amount, currency, merchant environment, checkout mapping and immutable local order reference. Reject/quarantine mismatches or unknown IDs; never trust return URL query parameters, a screenshot or WhatsApp text.
5. In one database transaction, apply permitted payment/order transition, convert reserved capacity to committed production and enqueue owner notification. Ensure uniqueness for fulfillment/notification transitions. Later pending/failed deliveries must not downgrade verified success.
6. A worker reconciles pending/unknown attempts and retries durable inbox work after outages. Admin has unresolved-payment and notification-failure queues. Refunds and disputes update financial state without pretending production was undone.

Items 2–6 are application design requirements, not provider guarantees.

**Schema discrepancy to resolve:** the unified migration/API contract uses `in_*`, while the webhook overview still shows a `pi_*` example. Sandbox documentation describes `eventType`, `eventId`, and `data.event_type` wrapping. Record real signed Sandbox fixtures and verify the enabled endpoint's exact envelope before freezing the parser; do not invent fields, accept arbitrary alternative shapes, or treat payload `id` as a universal event ID. [Unified API](https://docs.recurrente.com/referencia-api/api-reference/intents/get-intent), [Sandbox event envelope](https://docs.recurrente.com/guides-english/guides/sandboxes-and-test-clocks)

## Capacity and asynchronous payment: launch blocker

The inspected checkout API documents expiry but not a hard cancellation guarantee for a pending ACH intent. The bank-transfer guide explicitly allows delayed and unassociated credits. **The strict “cannot pay for an unavailable slot” requirement remains unverified.** A refund/rebooking procedure mitigates harm after payment; it does not meet that prevention requirement. [Checkout mutation restriction](https://docs.recurrente.com/referencia-api/api-reference/checkouts/update-checkout), [ACH matching and delays](https://ayuda.recurrente.com/es/p/como-pagar-por-transferencia-bancaria)

Proposed invariants:

- Reserve production atomically before exposing any provider URL. Reserved plus committed units must not exceed daily/product capacity.
- At local expiry, stop presenting the URL, reconcile provider state and invalidate the session where supported. Do not immediately resell a slot with a pending/unknown payment or unresolved provider creation.
- Keep a pending-transfer reservation until a proven terminal state/cutoff policy permits release. A ten-minute advertised transfer time is not a safe upper bound.
- Process late success as a visible financial exception; never silently discard received money or automatically overbook. Human refund/rebooking is a contingency and must not be advertised as prevention.
- Owner changes to closed dates/capacity must respect existing holds and confirmed orders.

Provider questions that block strict automatic release: Can expiry reject an already-started transfer? Can pending bank intents be canceled, with which endpoint and terminal response? Can an expired/failed/canceled intent later succeed or be manually associated? What is the maximum settlement/matching window? How are saved bank details and unmatched incoming money treated? Does card authorization/capture race expiry? What authoritative proof makes a reservation safe to release?

Smallest alternatives if the required guarantees are unavailable: **(A)** retain the slot until payment resolution, accepting lower utilization and an owner-approved longer deadline; **(B)** offer only payment methods with verified terminal expiry behavior; **(C)** use request-first ordering with owner-held capacity before issuing payment instructions. None should be labeled full compliance until its lifecycle is proven; an owner may explicitly choose a late-payment/refund policy as a changed business requirement.

## Refunds and testing limits

`POST /api/refunds` accepts unified `intent_id` (legacy `payment_intent_id` remains an alias). Use a unique `Idempotency-Key`; `GET /api/refunds/{id}` follows the result. Some processors support partial refunds; others only remaining-full refunds. Unknown provider outcomes can stay pending with `provider_outcome_unknown`; do not blindly issue another refund. The generic “compatible” methods language does **not** verify ACH refund availability or routing for Güteli. Obtain that method-specific contract. [Create refund](https://docs.recurrente.com/referencia-api/api-reference/refunds/create-refund)

The help center states refunds within 30 days, sufficient balance required, no installment refunds, and card receipt taking 3–25 business days. Fiscal timing can change the merchant debit. Confirm account/method-specific policy before publishing a customer refund promise. [Refund conditions](https://ayuda.recurrente.com/es/p/como-puedo-reembolsar-un-pago-a-un-cliente)

Sandbox supports simulated card success/decline, refunds and delivered test webhooks. It does not reproduce real bank authorization, 3DS or settlement; fixture events do not create corresponding financial objects. The old root introduction says test payments emit no webhooks, conflicting with the dedicated current test guide; use the dedicated guide and verify by test. Sandbox access needs administrator permission/invitation; production activation is separate. [First test payment](https://docs.recurrente.com/guias-espanol/comenzar/primer-pago-de-prueba), [older conflicting introduction](https://docs.recurrente.com/)

Future acceptance evidence must distinguish: local mocked contract tests; signed provider fixture delivery; simulated card end-to-end payment; and separately approved, capped real ACH/card validation. No real-money test is authorized by this research. ACH late-arrival/cancellation cannot be certified from card Sandbox tests.

## WhatsApp handoff and owner notification

The official Click-to-Chat format is `https://wa.me/<international-digits>?text=<URL-encoded-message>`. Recipient must have an active account; it works on phone and WhatsApp Web. The prefilled content appears in the message field: the customer must press Send and may edit or abandon it. This link provides no delivery/read callback or automatic owner alert. It needs no WhatsApp messaging-API integration; it is a customer action. [Official WhatsApp instructions](https://faq.whatsapp.com/5913398998672934)

Proposed UX: show a confirmed order page backed by verified server state, then “Open WhatsApp to send your order.” Include order number, customer name/telephone, item quantities, total labeled GTQ, pickup/delivery details, requested local date, notes and the server-verified payment status. Encode the whole text once; recipient is configured digits including country code. Avoid public analytics capture of message URLs containing customer details. Test accents, ampersands, line breaks, mobile/desktop behavior and bounded long notes.

The reliable discovery mechanism is the durable backend order record plus authenticated admin paid-order queue, unread acknowledgment and refresh/polling. A notification outbox may add an approved email channel with retries, but WhatsApp click/send cannot be the transaction commit or notification acknowledgment. Closing the browser immediately after payment must still produce an order visible to the owner. Owner must approve a check frequency/channel before launch.

## First implementation prerequisite

Complete a provider-contract/owner-decision ticket first: verify account activation and methods; capture signed Sandbox fixtures; establish checkout-create retry recovery; prove expiry and in-flight-payment behavior; document ACH refund/matching procedure; approve capacity policy and owner notification workflow. Its result is an evidence-backed launch-method choice. Subsequent tickets may implement local order/payment/capacity models, but real checkout enablement stays blocked until these questions are resolved.
